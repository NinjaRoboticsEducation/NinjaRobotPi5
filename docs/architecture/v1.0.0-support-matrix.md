# NinjaRobotPi5 v1.0.0 Support and Known Limitations

## Supported release target

| Area | v1.0.0 support |
|---|---|
| Host | Raspberry Pi 5, Raspberry Pi OS, Python 3.11–3.13 |
| Hardware ownership | One IDE/agent service process; six managed `pi5*` drivers |
| Model providers | Ollama plus API-key-only OpenAI, Gemini, and Anthropic |
| Voice | Local **Hey Ninja** wake word and local input transcription; no TTS |
| Voice languages | English, Japanese, Traditional Chinese, Simplified Chinese |
| Web UI | HTTPS portrait controller and the same four interface locales |
| Remote access | Optional pyngrok/ngrok account with one-use passwordless pairing |
| Identity/memory | Local multi-user face profiles and user-scoped Phase 7 memory |
| Boot | Explicitly enabled systemd real-hardware service with QR onboarding |

## Architecture and compatibility guarantees

- The agent reaches hardware only through `ninjarobot_pi5_ide`; voice,
  onboarding, direct controls, behaviors, and shutdown do not create alternate
  driver owners.
- Phase 7 profiles, face images/encodings, preferences, conversation database,
  behavior memory/catalog, model selection, calibration, safety state, and
  secrets retain their existing locations and schemas. Phase 8 enable/disable,
  upgrade, and uninstall do not erase them.
- Local and remote browsers keep independent transcripts/active-user choices
  while the selected user's long-term memory remains shared across interfaces
  and model changes.
- Managed driver imports remain at the recorded baseline plus 28 explicitly
  authorized repairs. `NinjaClawBot/` is neither imported nor packaged.

## Privacy and security boundaries

- Background microphone audio is processed locally, is not retained, and only
  a bounded command clip reaches local transcription after wake detection.
- Voice does not add TTS. Replies remain in web/display/behavior presentation.
- Voice and chat movement use the existing explicit `/arm` or **Arm AI motion**
  authorization and fail closed on restart, stop, disable, lease loss, or model
  replacement.
- QR pairing credentials remain in URL fragments, exchange once, expire, and
  become Secure/HttpOnly/SameSite sessions. Anonymous assets, WebSockets,
  direct controls, and power-off are rejected during onboarding/remote use.
- ngrok credentials and pairing secrets stay in owner-private files and never
  appear in QR codes, normal status, or events.
- Power-off is deterministic, paired, lease-bound, twice confirmed, nonce
  protected, and limited to one fixed root-owned helper after cleanup. Pi 5
  full-PMIC shutdown must also be active in EEPROM; deployment schedules the
  official setting and web shutdown remains fail-closed until the next reboot
  applies it. Runtime preflight also verifies the fixed helper's exact content,
  ownership, non-symlink identity, and mode.

## Known limitations and residual risks

- Live wake accuracy, long-duration microphone/resource stability, ngrok
  account behavior, multilingual UX, display readability, Greeting motion,
  reboot, and physical power-off still require the documented Raspberry Pi
  acceptance checklists. Software completion is not a physical pass.
- The custom wake model may require future dataset expansion for accents and
  noisy rooms. Its present provenance is approved, but the repository does not
  claim universal recognition accuracy.
- Browser speech recognition is browser/service dependent; manual USB capture
  and local transcription are the privacy-preserving alternative.
- ngrok availability, free-tier interstitials, quotas, endpoint policies, and
  internet routing are external service constraints. Local fallback requires a
  real remote failure and a client able to resolve `.local`.
- Passwordless QR pairing treats physical access to the display as consent.
  There is no owner PIN or strict educational-project authentication layer.
- Face recognition is local convenience identity, not biometric security.
- Voice output/TTS, multi-agent orchestration, and automatic user switching by
  voice are outside v1.0.0.
- A compromised non-root service could invoke the one permitted power-off
  helper, causing availability loss, but cannot receive arbitrary sudo through
  the installed rule.

## Publication status

The source is a v1.0.0 release candidate after the final software gate. Do not
create or publish the `v1.0.0` Git tag until the operator completes and signs
the Phase 8 Raspberry Pi validation records and explicitly approves public
publication.
